# simplify

JOB: reduce the code and complexity that carry current behavior, without code golf or behavior changes.
IN: a completed code change or named code scope, plus the repository and its test commands.
OUT: a verified edit and a fixed report with tests, reductions, and control-flow and algorithmic complexity evidence.

## process

1. Start from the changed symbols, not only the changed lines.
2. Trace their callers, callees, events, shared state, persistence, errors, and external boundaries.
3. Add every module whose behavior or side effects the change can affect.
4. Stop the expansion where neither behavior nor side effects can change.
5. Read the project instructions and every module in the scope.
6. Find the narrowest test command that covers the full scope.
7. Run that command before any simplify edit.
8. Stop without edits if the baseline fails. Report the failing command and result.
9. Run `rust-code-analysis-cli --metrics --output-format json --paths <file>` for each changed Rust, TypeScript, JavaScript, or Python file.
10. Finish the analyzer step when every supported changed file has JavaScript Object Notation (JSON) output.
11. Walk each JSON `spaces` tree. Keep records where `kind` is `function`.
12. Report each function name, line range, and cyclomatic metrics.
13. Re-run the analyzer after each control-flow reduction. Report the before and after values.
14. Stop if `rust-code-analysis-cli` is absent. Run the managed agents installer before the next simplify pass.
15. Do not invent a complexity score.

Review algorithmic complexity after the scope trace:

1. Find every operation in the traced scope whose time or storage can grow with an input.
2. Analyze each relevant operation even when you keep its code unchanged.
3. Include loops, recursion, searches, sorting, repeated scans, allocation, copying, and data-structure operations.
4. Name each independent input-size variable. Keep `n` and `m` separate unless evidence proves that they grow together.
5. Trace loop bounds, caller limits, callee behavior, collection guarantees, and documented library costs.
6. Keep unknown caller, callee, collection, or library behavior unknown. Do not infer a bound from syntax alone.
7. Record the operation and the static or documented evidence for each bound.
8. Report time and auxiliary-space bounds with applicable worst-case, average-case, expected, or amortized qualifiers.
9. Report returned output storage separately when its size grows with an input.
10. For recursion, report branching, input reduction, work per call, and maximum live stack depth.
11. Use maximum live call depth for recursion space. Use tail-call elimination only when the supported runtime guarantees it.
12. Treat each fixed enforced bound as constant. Do not propose an edit only to optimize that bound.
13. State `no input-sized operation` when no reviewed operation grows with an input.

Sequential work adds costs. Nested input-sized work multiplies costs. Independent inputs stay independent.

Static evidence can prove an asymptotic bound and an asymptotic change. Measure before you claim a practical speed or memory benefit.

Inspect the scope in this order:

1. Remove unused imports, variables, functions, branches, and obsolete compatibility code.
2. Merge repeated logic when one direct form is clearer than the copies.
3. Reduce input-sized work when the lower bound also keeps the code clear.
4. Reduce measured control-flow complexity when the reduction also makes the code clearer.
5. Inline a single-use helper when its name or boundary adds no useful meaning.
6. Replace verbose loops, chains, and conditionals with clear language or standard-library forms.
7. Remove defensive checks only when the type system proves that the state is impossible.

Search all references before you remove or inline a symbol. Check generated, reflective, configured, and externally used entry points.

Use the language and library versions that the repository supports. Do not modernize past those versions.

Prefer fewer concepts, branches, and repeated words. A lower line count is evidence only when the structure also becomes simpler.

Cyclomatic and algorithmic complexity are review signals. They are not targets. Keep clear bounded code when an optimization adds needless complexity.

Keep a high cyclomatic score when flat branches are the clearest form. Never add a helper only to lower the score.

Keep a candidate unchanged when it does any of these jobs:

- Names a domain concept that would disappear inside its caller.
- Separates side effects, ownership, error handling, or a public boundary.
- Makes the common path easier to read.
- Guards data that enters from outside the type-checked boundary.
- Needs a dense expression, chained ternary, hidden mutation, or compressed control flow.

Apply only candidates whose behavior is clear from the code and tests. Do not add an abstraction to support a possible future use.

Accept an algorithmic edit only when it preserves behavior and the same baseline test command passes.
Report complete before-and-after time, auxiliary-space, and output-space bounds for each accepted algorithmic edit.
Include independent inputs, operation evidence, case qualifiers, and recursion stack depth when applicable.

Run the same baseline test command after the edits. Restore only this pass's edits if the command fails.

Run the repository formatter and static checks for the changed files. The pass is complete when all checks pass.

## report

Return exactly these fields:

```text
Scope: <affected modules and side-effect boundaries>
Baseline: <command and result>
Reduced: <removed symbols, branches, repetitions, boilerplate, or input-sized work>
Kept: <valuable candidates left unchanged, including analyzed input-sized operations, or none>
Complexity: <cyclomatic records; every relevant algorithmic operation with inputs, evidence, qualified time, auxiliary space, output space, and recursion depth; before → after or kept reason>
Final: <same baseline test, formatter, and static-check results>
```

Do not claim a reduction from formatting, statement packing, renamed short identifiers, or deleted tests.
