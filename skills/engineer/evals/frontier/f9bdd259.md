# engineer

JOB: Carry one task from a research base to a landed, signed-off change.
IN: A task: a backend id plus short or long text from `/pick-task`, or a plain description.
When no task is available, step 0 dispatches `/pick-task` and uses its selection.
OUT: Land the change through `/git-sync`, with a PR when the repository has a remote.
Without a remote, `/git-sync` lands a local squash merge.
Include the signed manual-test checklist and the applicable visual evidence.
Keep the working notes in the gitignored `.context/<task-slug>/` directory.

## working notes

Keep everything that this run writes in `.context/<task-slug>/` while the work continues.
This content includes the research summary, the plan document, the test results, and the visual evidence.
The `.gitignore` file excludes this directory.
The directory contains scratch content for this run, not project artifacts.
Never stage or commit content under this directory.
When a step changes tracked repository paths, commit those paths directly.

## 0. get a task

When no task is available, dispatch `/pick-task` and use its result.
Then, continue the process.
When a task has an id or a clear description, start Research directly.

Before Research starts, change the status of a backend-tracked task to in-progress.
A backend-tracked task is a GitHub Issue, a Linear item, or a `roadmap.json` entry.
For GitHub, set the native Status field of the project.
Use the convention from `task-graph`:

`skills/task-graph/scripts/gh-issue-field.sh <id> Status in-progress`

For Linear, use MCP(Model Context Protocol) to move the issue to its "In Progress" state.
For `roadmap.json`, set the `status` field of the entry to `in progress`.
A one-off description without a backend id has no status to change.
Skip the status change for that description.

Append the id to `.context/branch-tickets.md`, with one id on each line.
Create the file when the branch receives its first task.
Close uses this file in step 7 to find every ticket that the branch carries.
The file also records a second task that the branch receives before Close.
Thus, Close does not derive the ticket list from memory.

**Folding a second ticket into the same branch.** This process does not require a new branch for each task.
Engineer and `/git-sync` branch from main only when work starts on main itself.
This rule comes from step 3 of `/git-sync`.

By default, another engineer run continues on the same feature branch.
This behavior applies when that branch contains unfinished or unlanded work.
Change the status of the new task by use of the same process.
Append its id to `.context/branch-tickets.md` beside the first id.
Process it through Research → Plan → Implement → Simplify → Test as any other task.
Land both tasks through one Close.

## 1. Research

Dispatch the research workflow at `workflows/research-sweep/` with a goal from the task.
Research what exists today, how the current implementation works, and what the change will touch.
Also research the external angles that the task needs.
The plan node of the workflow selects the applicable web, academic, design/UX(user experience), and news angles.
Write the returned findings blocks to `.context/<task-slug>/research.md`.

**Check it before building on it.** Show the summary and wait for approval.
A wrong finding is least expensive when the user finds it here.
Every later step uses this finding for its plan.

## 2. Plan

Write `.context/<task-slug>/plan.md`.
At a minimum, include the following sections and decisions.

- **UX(user experience) decisions.** Include the before and after states.
  Name the selected interaction pattern and the rejected pattern.
  State the intended feeling and action.
  Use `/vocabulary` for exact terms.
  Use `/show-me` for a before-and-after diagram when a picture communicates faster than prose.
- **Data-structure decisions.** Include every type, field, and persisted shape.
  Include declarations only, without bodies.
  Probe every externally owned shape against the real object instead of its documentation.
  Paste the probe output beside the declaration.
  Use `/show-me` for a shape diagram when the work has more than two types.
- **Harness-shaped tasks route through /ai-author first.** Treat a checker in `tools/` as harness-shaped.
  A hook or a skill, agent, or workflow edit is also harness-shaped.
  For such work, run the should-it-exist check from /ai-author before you write this plan.
  /ai-author routes the work to tool-author, skill-author, agent-author, or workflow-author.
  Product-code tasks skip this item.
- **TDD(Test-Driven Development) or not.** Name the decision and its reason.
  Tests-first suits a shape that has a clear contract and useful edge cases before code exists.
  Tests-after suits exploratory or UI(user interface)-heavy work when the shape still changes.
  In both cases, Test in step 5 still runs.
- Read `invariants.md` at the repository root during this step.
  Include each invariant that applies to this task.
  Engineers use these standing rules before they commit to a shape.

**Get feedback on the plan before building it.** Check whether this session has `plannotator_submit_plan`.
When the tool is available, write the plan and submit it through that tool.
The approval loop is the gate.
When the user denies the plan with feedback, revise the plan and submit it again.
Keep the UX and data-structure decisions as sections in the one file that the tool reviews.
Do not create separate custom protocols.

When the tool is not available, show `plan.md` directly.
Wait for an explicit yes before you continue.
In both paths, do not create a manifest or hash a snapshot.
The plan file and a one-line verdict log form the record.

## 3. Implement

Build the change.
By default, use one simple, sequential pass through the plan.
Use `/task-graph` only when the task is large enough for disjoint-file parallel work to repay its coordination cost.
Make this a deliberate, named decision at this step.
Never use `/task-graph` as the default path.

When the build differs from the plan, state the difference clearly.
Then, add the difference to `plan.md` instead of silently accepting it.

## 4. Simplify

Run `/simplify` on the completed implementation before any fresh-context test or review starts.

Require `/simplify` to run its baseline, complexity review, final tests, formatter, and static checks.
Stop when any required check fails.

Record the full simplify report in `.context/<task-slug>/simplify.md`.
Continue when the report makes no edit and all required checks pass.

Test and review the difference after simplification.
The simplify checks never replace independent testing or review.

## 5. Test

Dispatch fresh-context testers against the cases in the plan.
Use `spec-tester`, `maestro-tester`, or both, as appropriate for the surface.
Pass each tester a `change_scope` that states whether the change alters what a user can see or do.
Give Maestro an `evidence_dir` under `.context/<task-slug>/`.
For a qualifying spec test, include an applicable capture command in the drive matrix.

Require visual evidence only when the change alters what a user can see or do.
A refactor, dependency change, test change, or technical-debt change needs no visual evidence in one condition.
Visible and interactive behavior must stay the same.
For other work, testers return media only when it helps to verify or explain the result.
Use screenshots for static states.
Prefer before-and-after screenshots when a comparison helps.

Use a short screen recording when time or interaction carries the result.
This requirement includes animation, gestures, drag-and-drop, navigation, focus changes, and transitions.

Collect each tester's `visual_evidence` items in `.context/<task-slug>/visual-evidence.jsonl`.
Write one JSON(JavaScript Object Notation) object on each line.
Include `path`, `media_type`, `label`, and `alt` in each object.

Use `null` for the alternative text of a video.
Resolve each path.
Verify that each file exists.
Verify that each path stays in `.context/<task-slug>/` or the declared scratch directory of the tester.

Do not stage the manifest or its evidence files.

Dispatch a fresh-context `code-reviewer` over the difference.
Pass the evidence manifest when the difference alters what a user can see or do.
The reviewer must inspect every entry.
Treat a missing or incomplete visual review as a test failure.

Neither verifier shares context with the agent that built the change.
A verifier that reads the chat of the builder grades its own work.
Record each failure clearly.
Fix each failure.
Run the affected tester and reviewer again.

## 6. Minimal manual test + signoff

Write six to eight plain-language bullets.
Keep each bullet under 75 characters.
Each bullet must name exactly what a human must click or run to confirm that the change works.
Show the checklist and wait for the manual verdict.
This gate is the last stop before the change leaves the machine.

## 7. Close

Dispatch `/git-sync` for the complete landing sequence.
The sequence commits, pushes, and opens or updates the PR(Pull Request).
Without a remote, the sequence makes the local squash merge.
It also prunes the branches that main already contains.
Pass `.context/<task-slug>/visual-evidence.jsonl` when it exists.
Pass every id from `.context/branch-tickets.md`.

For each GitHub Issue id, `/create-pr` adds a `Closes #<id>` line to the PR body.
This line makes the PR merge close the issue automatically.
For each `roadmap.json` id, change its `status` to `done` during this step.
No equivalent PR merge action exists for `roadmap.json`.
Do not leave this status change for a later run.

For a Linear item without a linked GitHub issue, use MCP(Model Context Protocol) to move its state to "Done" directly.
The same reasoning applies.
Never implement any part of that sequence again in this skill.

## evals

`evals/run.sh` grades every non-holdout case in `evals/cases.jsonl` against this file or a candidate.
It uses `evals/rubric.md`.
`--holdout` runs the held-out slice.
