# phase 08 — task-breakdown

JOB: all remaining work decomposed into the smallest atomic tasks, each independently verifiable and owned by named files
IN:  data-structures.md, interfaces.md, call-stacks.md, testability.md (harness-gap tasks); phase 07 committed
OUT: `.map/<ID>/tasks.json` (all statuses todo, deps empty for now)

## steps

1. decompose the work: one concern per task, completable by one agent in one sitting, independently verifiable. A `long` that joins two concerns with "and" is two tasks. Done when no task fails the one-concern test.
2. write each task as a task-graph object into tasks.json. The ids are `<ID>.T<NN>` in creation order. `kind` is `code` or `command`. Each task carries a short, a long, and a `files` array. The long is fresh-agent-executable: it names the files, the contracts, and the edge conditions. `files` is MANDATORY and non-empty for code tasks, because parallelism and the stash content check both ride on it. Done when every task parses against the schema.
3. include the harness-gap tasks from phase 04 and the FIX lines from phase 05. The FIX lines file as `kind: command`. Include nothing speculative. Done when both lists are covered and nothing else crept in.
4. count the tasks. Over 25, run conditional HUMAN GATE SPLIT. Before the gate, project the exact post-split artifacts: retained tasks.json; parked tasks with their boundary and both dependency directions; and every phase-06 declaration, phase-07 signature, and call-stack level assigned to either side. Apply STANDING APPROVAL from SKILL.md over that complete projection. On the first approval or a decisional delta, STOP and put it to the user; he adjusts or approves the boundary and selects which side this ticket keeps. An equal or prose-only re-entry carries approval and continues without stopping. Over 25 tasks, carrying the whole graph forward is not an option. `state.json.gates.SPLIT` records the verdict, approval number, and immutable snapshot. At 25 or fewer tasks with no existing `state.json.gates.SPLIT`, the gate does not fire and no entry is written. When a SPLIT entry already exists, re-entry always rebuilds the approved projection from retained tasks plus the parked file and applies STANDING APPROVAL, regardless of the retained count. On approval, write the parked projection to `.map/<ID>/parked-ticket-candidates.json`; phase 21 must carry it into exploration.md, and phase 22 alone may file it after GATE D. If the parked side owns any declaration, signature, or call-stack level already present, open one walk-back to the earliest of phase 06 or 07, prune those parked deltas from this ticket, and walk forward to phase 08. The re-entered gate presentation rebuilds from retained tasks plus the parked file, matching the approved projection when the boundary was applied exactly. Phase 08 never writes roadmap.json. Continue only when tasks.json holds the retained set and every remaining phase-06/07 delta belongs to it. It exists because ticket size is what drives replan cost: the four recorded runs opened 3, 3, 11, and 32 walk-backs against 5, 7, 20, and 107 tasks.
5. check the coverage: every struct and signature delta from phases 06-07 is covered by ≥1 task. Every side-effect that call-stacks.md records needs a task too. A side-effect with no task is work nobody owns. Commit `map(<ID>): phase 08 task-breakdown`.
